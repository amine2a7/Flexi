# Besoins de contrat exprimés par les specs d'écran (web d'abord)
**Auteur :** design · **Créé :** 2026-10-11 · **Destinataire :** backend (tâche WB2, `docs/handoff/contracts/openapi.yaml`)
**Statut :** proposition. Le contrat reste la source de vérité : backend peut renommer, découper ou refuser ; design adapte alors les specs. Les noms ci-dessous sont des **propositions** conformes aux conventions du contrat (`/v1`, `camelCase`, `…Millimes`, `…Bps`, `Timestamp` UTC, `CalendarDate` `Africa/Tunis`, pagination par curseur, Problem Details, `Idempotency-Key` sur toute opération financière).

Légende : **E** = existe déjà dans le contrat (schéma ou code) · **N** = à créer · **?** = question ouverte, la spec d'écran ne présume pas de la réponse.
Règle de design rappelée : **le front n'affiche que ce que l'API renvoie.** Aucun calcul (commission, frais, plafonds, soldes, pourcentages, échéances, totaux) n'est fait côté client ; tout nombre affiché vient d'un champ ci-dessous, déjà en millimes (`…Millimes`) ou en points de base (`…Bps`).

Chaque besoin porte un identifiant `CT-<espace>-<n>` repris dans la section « Données » de la spec de l'écran.

## 1. Commun (WD1) — authentification, session, profil

Séquence d'enchaînement souhaitée côté écrans (à confirmer, **CT-C-0**) :
`/login` → [si mot de passe temporaire] `/password/change` → [si MFA non enrôlée] `/mfa/enroll` → [sinon si MFA requise] `/login/mfa` → espace de l'utilisateur (`/admin`, `/company`, `/merchant`).
Le web ne sert que `ADMIN`, `COMPANY` (tous sous-rôles) et `MERCHANT` (tous sous-rôles). `EMPLOYEE` et `FAMILY_MEMBER` utilisent l'application mobile (cahier §1.2).

**Réponses de backend (contrat 0.2.0, 2026-10-12) — ce bloc l'emporte sur le tableau ci-dessus :** CT-C-0 : la MFA est vérifiée **avant** toute session ; MFA enrôlée → `/login/mfa` → (mot de passe temporaire) `/password/change` → espace ; MFA non enrôlée → session restreinte → `/password/change` si temporaire → `/mfa/enroll` → espace. CT-C-1 : `LoginResult` = `MfaChallengeResult` ou `SessionResult` (`nextStep`, `csrfToken`, `challengeId`, `challengeExpiresAt`). CT-C-1b : confirmé (même `INVALID_CREDENTIALS`). CT-C-1c : `403 FORBIDDEN` après vérification du mot de passe. CT-C-2 : TOTP 6 chiffres, `MFA_CODE_INVALID`, `MFA_CHALLENGE_EXPIRED`, défi 5 min usage unique. CT-C-3 : `{ otpauthUri, secretBase32, expiresAt }`, **QR généré côté client**. CT-C-3b : `enroll/confirm` → `SessionResult` ; codes de secours : principe Must (SEC-A4), forme en attente. CT-C-4 : `CURRENT_PASSWORD_INVALID`, `PASSWORD_POLICY_VIOLATION` (`params.rule`). CT-C-5 : `GET /auth/password-policy` → `rules[]` (`MIN_LENGTH`, `MAX_LENGTH`, `NOT_COMPROMISED`, `NOT_IDENTIFIER`, `DIFFERENT_FROM_CURRENT`). CT-C-8 : `Me` = `id`, `displayName` (prénom + initiale), `role`, `subRole|null`, `permissions[]` (`module.action`), `tenant { id, label }|null`, `mfa { required, enrolled }` — **pas** de `mustChangePassword`, pas encore de `unreadNotificationsCount`. CT-C-9/10 : forgot → 202 ; reset `{ token, newPassword }` provisoire (jeton dans le fragment `#token=`, 15 min, usage unique, **décision en attente**) ; aucune session ouverte après réinitialisation. `page.count` : toutes les listes paginées (§7). Statuts : « À régler » = `CONFIRMED` (aucun `ReceivableStatus`) ; `EXPIRE` / `SUSPECT` non définis (décision demandée à `main`, repli `INCONNU`). **Demandes de securite à backend (ux N-02) :** retrait de `currentPassword` en session restreinte, session restreinte 10 min absolue à usage unique, `restrictedUntil` fourni par l'API (CT-X-6).

Points de sécurité transmis à `securite` avec la spec : contenu et validation de `returnTo` (chemin relatif interne uniquement), absence d'oracle de compte/rôle, secret MFA affiché une seule fois, aucun jeton en mémoire persistante, champs `autocomplete`, aucune donnée sensible dans l'URL ni dans les analytics.

## 1bis. Transverse (composants de `dev-composants.md`)

| ID | Besoin | Détail |
|---|---|---|
| CT-X-1 | Compteur de résultats borné | **Réponse backend du 2026-10-11, acceptée par ux.** `?withCount=true` au premier chargement et à chaque changement de filtre (jamais en tournant les pages) ; `page.count { value, isLowerBound }`, plafond 10 000 ; toutes les listes paginées (contrat 0.2.0 §7). À ajouter à `PageInfo` (champ facultatif, non cassant). Si absent : aucun compteur affiché |
| CT-X-2 | Filtres de période en dates calendaires | Le contrat n'a que `createdFrom` / `createdTo` (`Timestamp` UTC). Le front ne doit pas convertir « du 3 au 10 octobre » en bornes UTC (jour tunisien) : **proposer `fromDate` / `toDate` en `CalendarDate` (`Africa/Tunis`, bornes incluses)** sur les listes à filtre de période |
| CT-X-3 | Exports asynchrones | `POST /v1/exports` `{ type, format, filters }` (+ `Idempotency-Key` recommandée) → `Export { id, status: PENDING \| READY \| FAILED, downloadUrl?, expiresAt? }` ; `GET /v1/exports/{id}` ; lien **signé de courte durée**, isolation par tenant (spec 09 §3-4). Formats autorisés par `type` fournis par l'API |
| CT-X-4 | Envoi de fichiers | Le contrat §8 n'accepte que `application/json` (`415` sinon). | CT-X-5 | Heure serveur | Les écrans à compte à rebours (code client 60 s, blocage `RATE_LIMITED`) ont besoin de `expiresAt` **et** de l'heure serveur `serverTime` (ou `expiresInSeconds`) pour ne pas dépendre de l'horloge de l'appareil |
| CT-X-6 | Avertissement d'expiration de session | Durées d'inactivité et absolue (WCAG 2.2.1, revue ux UX-17) : à fournir par `securite` / backend (par `GET /v1/me` ou en-tête) ; design ne les fixe pas |
| CT-X-7 | Notifications | `GET /v1/me/notifications` (liste paginée), `POST /v1/me/notifications/read` ; schéma `Notification { id, type, titleKey/params, objectRef { type, id }, createdAt, read }` ; voir `navigation.md` N.8 |
